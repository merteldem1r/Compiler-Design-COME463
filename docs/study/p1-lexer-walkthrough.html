How the Anka lexer works, from zero

A plain-language tour of what we are building, why, and what every file and every important line of code does. Read it top to bottom once; then use the playground (§13) to experiment.

1. What are we building?

This semester we build one compiler for our own programming language, called Anka (files end in .anka).

A compiler is a program that reads code written by a human and translates it into something a machine can run. It's too big to write in one go, so it is built like an assembly line: each station does one job and passes its result to the next. We build one station per project:

2. What does a lexer do?

Think about reading "thecatsatonthemat". Before you can understand the sentence, your brain has to split it into words: the · cat · sat · on · the · mat. A computer has the same problem. To it, a program is just one long row of characters:

let␣x:␣int␣=␣42;

The lexer reads those characters left to right and groups them into meaningful "words", called tokens:

LETIDENT xCOLONTYPE_INTASSIGNINT_LIT 42SEMI

The lexer has four jobs:

  1. Group characters into tokens (4,2 → one number 42).
  2. Throw away what doesn't matter: spaces, tabs, newlines, comments.
  3. Remember the line number of every token, so later error messages can say "line 7".
  4. Report characters that don't belong (like @), then skip them and keep going. It never stops at the first error.

Why bother? Because the next station, the parser, then works with 7 clean tokens instead of 16 raw characters. It never has to think about spaces or comments again.

4. The two rules that decide everything

Often several patterns match at the same spot. For the input ifx, the keyword pattern if matches the first 2 letters, and the identifier pattern matches all 3. Which one is right? Every lexer (and Flex) uses two rules, straight from lecture 2:

Rule 1, maximal munch: the longest match wins.
Take as many characters as any pattern can match.

Rule 2, priority: on a tie in length, the rule written first wins.
The order of the rules in our file matters.

InputWho matches (how many characters)Winner, and which rule decided
=="=": 1 · "==": 2EQ by munch
ifxkeyword if: 2 · identifier: 3IDENT ifx by munch
ifkeyword if: 2 · identifier: also 2IF by priority (keywords are written first)
007integer: only 0 (1) · leading-zero error rule: 3ERROR by munch
a-->bat -: only "-" fits · then at ->: "->" 2 beats "-" 1IDENT MINUS ARROW IDENT

If you remember only one thing from this page, remember these two rules. Almost every "why does it do that?" question about the lexer is answered by one of them.

5. We don't write the matching code: Flex does

We could write the lexer by hand, with a giant pile of if (c == 'l') ... statements (lecture 2 shows one; it's long and easy to get wrong). Instead we use a tool called Flex:

  1. We write a list of rules. Each rule is a regex plus a bit of C code to run when it matches.
  2. Flex turns all the regexes together into one DFA, a state machine, using exactly the steps you are doing by hand in Part A: regex → NFA (Thompson) → DFA (subset construction) → minimized DFA.
  3. Flex writes that DFA out as a C file (lex.yy.c), with a function yylex(). Each time you call it, it gives you the next token.

So Part A (theory) and Part B (code) are the same thing from two sides. In Part A you build the machine by hand; in Part B Flex builds it for you from our rules.

7. src/tokens.h: the token list

Purpose. The lexer and the driver must agree on what each token is. In C the simplest way is to give each token a number, with a readable name for it. That is what an enum does.

src/tokens.h (shortened)
  • enum numbers names automatically. FN = 258, so LET becomes 259, IF 260, and so on. When the lexer sees let it returns 259; the driver knows that 259 means LET.
  • Why start at 258? This is Bison's convention (Bison is the parser tool we use in Project 2), and the professor's example does the same: numbers 0–255 are reserved for single characters, 256–257 are used internally, and real tokens start at 258. Following it now means P2 needs no renumbering.
  • Why END = 0? Bison expects the lexer to say "the file is finished" by returning 0, so we give 0 a readable name.
  • #ifndef TOKENS_H … #endif is an include guard. If two files include this header, it is still only read once, which avoids "defined twice" errors. It's standard boilerplate for every C header.

8. src/lexer.l: the rules (the heart of the project)

Purpose. This file says which text becomes which token. Flex reads it and generates the real scanner. A Flex file always has three parts, separated by %%:

8.1 The settings line

OptionWhat it means
noyywrapWhen the file ends, simply stop. (Otherwise Flex asks a function yywrap() whether there's another file to read, and we would have to write it.)
nounput noinputDon't generate two helper functions we never use, which would cause "unused function" warnings.
yylinenoFlex counts lines for us in a variable called yylineno: every time any rule reads a \n, it adds 1. This is how each token knows its line number.

8.2 The C helper block %{ … %}

Everything between %{ and %} is copied unchanged into the generated C file. We put our variables and two small helper functions there.

  • #include "tokens.h" lets the rules say return LET; using the names from §7.
  • lex_errors counts errors. At the end, main.c looks at it to decide the program's exit code.
  • comment_depth and comment_start_line are needed for nested comments (§8.6).
  • lex_error(...) prints one error in our standard format, for example LINE 3: ERROR unexpected character '@', and adds 1 to the counter. %-12s means "print this text padded to 12 characters", which keeps the columns lined up.
  • static means "private to this file": nothing outside the lexer can touch it.

8.3 Regex nicknames

Short names for regexes we use more than once, so the rules stay readable: {DIGIT} inside a rule means [0-9]. EXPONENT is the e10 / E-3 tail of a float. %x COMMENT declares a second mode for the lexer (explained in §8.6).

8.4 How a rule works

Each rule is pattern, then action in braces. Inside the action, two variables are always available: yytext holds the matched text, and yylineno the current line.

Two kinds of action:

  • It returns a token, e.g. { return LET; }. Then yylex() stops and hands the token to whoever called it (our main.c).
  • It doesn't return, e.g. whitespace, comments and errors. Then Flex simply keeps scanning. That is how "skip" works.

8.5 Whitespace and // comments: skip them

  • Rule 1: one or more spaces, tabs, \r (from Windows line endings) or newlines. The action is empty, so they disappear.
  • Rule 2: two slashes, then any characters except newline. So a // comment eats the rest of the line, and nothing else.

8.6 Block comments /* … */, which nest

In Anka, comments can contain comments: /* a /* b */ c */ is one comment. That's useful: you can comment out a piece of code that already has comments in it.

Why a regex can't do this: to know which */ closes which /*, you have to count. A DFA has a fixed, finite number of states, so it cannot count without limit (lecture: "a finite automaton cannot count"). So we add a small counter in C. This is a great point to mention in the report and in class.

The lexer has two modes:

  • INITIAL, the normal mode, where all the token rules are active.
  • COMMENT, "we are inside a comment". Only rules starting with <COMMENT> are active here. (The x in %x means exclusive: every normal rule is switched off, so a keyword inside a comment is never seen as a keyword.)

Step by step:

  1. Seeing /* in normal mode: set depth to 1, remember the line, and switch to comment mode with BEGIN(COMMENT).
  2. Another /*: depth + 1. A */: depth − 1. When depth reaches 0, switch back with BEGIN(INITIAL).
  3. Any other text: skip it. Ordinary text is skipped in big chunks; a single / or * (as in a*b) is skipped by .. Munch makes sure */ (2 characters) beats . (1).
  4. <<EOF>> means "the file ended". If that happens inside a comment, the comment was never closed. We report it at the line where it opened, because that's where the programmer needs to look.

8.7 Keywords, then identifiers (order matters!)

  • Quoted text means "exactly these characters". The 16 keywords come before the identifier rule. On while, both match 5 characters, so it's a tie and priority picks the keyword.
  • If we moved the identifier rule to the top, every keyword would become an IDENT, which is the classic beginner bug.
  • An identifier starts with a letter or _, then any number of letters, digits or _. So _tmp and x1 are identifiers; 1x is not, because it starts with a digit.

8.8 Numbers

RuleMeaningWhy
Float with a dotdigits, a real dot ".", digits, optional exponentDigits must be on both sides of the dot, so 1. and .5 are not floats. That's what makes 0..5 work: 0. can never start a float, so the lexer reads 0, then .., then 5.
Float with exponent onlydigits + exponent1e10 is a float even without a dot.
Integer0 alone, or starting with 1–9No leading zeros: the same idea as Part A question A1.1(d).
Leading-zero error0 followed by more digitsExists only to catch 007. Without it, munch would read 007 as three tokens 0 0 7, which is confusing. This rule matches 3 characters and beats the integer's 1, so the whole thing is reported as one clear error.

Note: "." in quotes is a real dot. A bare . in Flex means "any character". Also, 007.5 is a valid float (your decision, same as Python): the float rule matches 5 characters and beats the error rule's 3.

8.9 Strings

Read the first pattern piece by piece:

  1. \" an opening quote,
  2. ( … )* then zero or more of:
    • [^"\\\r\n] a normal character (not a quote, not a backslash, not a line end), or
    • \\[^\r\n] a backslash followed by any character except a line end (an escape, like \n or \"),
  3. \" a closing quote.

That's why "say \"hi\"" stays one string: \" is read as an escape, so it doesn't close the string.

The second rule is the same without the closing quote. If the string is closed properly, rule 1 matches one character more (the "), so munch picks it. If the line ends before any closing quote, only rule 2 can match, and we report "unterminated string". Munch alone decides; there is no if anywhere. The line end isn't consumed, so the next line is read normally.

Two bugs our tests found here (bugs #2 and #3 for the report).

  • #2: print("abc\ followed by a newline gave two errors: "unterminated string" and "unexpected character '\'". The escape part needs a character after the backslash, and a newline doesn't count, so the lone \ was left over for the catch-all rule. Fix: the unterminated rule ends with \\?, an optional lone backslash, so it is part of the one error.
  • #3: Windows files end lines with \r\n. The old pattern excluded \n but not \r, so the invisible \r ended up inside the error text and scrambled the message in the terminal. Fix: exclude \r too ([^"\\\r\n]); the \r is then skipped as whitespace.

Each fix has a test that fails on the old lexer: strings_comments.anka case C32 and crlf_line_endings.anka case C33.

8.10 Operators and punctuation

One rule per symbol, and no lookahead code at all: munch automatically makes ** one POW instead of two STARs, and == one EQ instead of two ASSIGNs.

8.11 End of file, and the safety net (last rule!)

  • End of file: return END (0), so the driver stops asking for tokens.
  • . matches any one character, which makes it the safety net (lecture 2: "write a rule matching all bad strings, put it last"). It is last and matches only 1 character, so it can only win when no other rule matches at all, like @ or #. We report the character, skip it, and continue: "report, skip, continue".
  • Why hex? A Turkish letter like ı is stored as two bytes (C4 B1) in UTF-8. Printing half a letter shows garbage, so for any byte that isn't normal printable ASCII we print its code instead, e.g. '\xC4'.
  • (unsigned char): in C, a plain char can be negative for bytes above 127, and isprint() must not receive a negative number. The cast prevents that bug.

9. src/main.c: the driver

Purpose. The lexer only finds tokens. Something has to open the file, keep asking for the next token, and print the results. That's the driver, the same role as test.c in the professor's example.

9.1 Borrowing the lexer's variables

These all live in the generated lex.yy.c. extern tells the C compiler: "this exists in another file; trust me, the linker will connect them".

9.2 Number → name

The lexer returns numbers (259); people want names (LET). A plain switch is long, but easy to read and impossible to get out of order.

9.3 main(): the loop

  1. Check the command line. It must be ankac --tokens [file]; otherwise print how to use it and exit with code 2.
  2. Open the file and point Flex's yyin at it. With no file name, Flex reads from the keyboard (standard input).
  3. The loop. Each yylex() call runs the rules until one returns a token, so spaces, comments and errors are handled inside that call. We print the token, then ask again, until END.
  4. Exit code: 0 means "clean", 1 means "there were lexical errors". Scripts, and later our parser, can check this number without reading the output.

Why print here and not inside the rules? The professor's example prints inside each rule. We keep the rules "pure" (they only return), because in Project 2 the parser will call yylex() directly and needs tokens, not printouts. This way the lexer needs no changes in P2.

11. Where the build/ folder comes from

You never create build/ by hand. The make command creates it, by following the recipe in our Makefile. Everything inside is generated from our three source files.

Three facts to remember about build/:

  • Never edit anything in it. Your changes would be overwritten by the next make.
  • Never commit it to git (it's listed in .gitignore). Anyone can regenerate it from src/.
  • Safe to delete at any time: make clean removes it, and make builds it again in about a second.

11.3 Step 1 · flex: rules become a DFA written in C

This is where Part A becomes real. Flex takes our 62 rules (61 written by us, plus one default rule Flex always adds), combines all their regexes, and runs regex → NFA → DFA → minimized DFA on them. The result is a single DFA with 130 states, which Flex writes into lex.yy.c as C arrays (tables). The most important ones:

TableWhat it stores
yy_ec[256]For every possible byte (0–255): its character class. Characters the DFA treats identically get the same class number.
yy_accept[130]For every state: is it accepting? If yes, for which rule.
yy_nxt, yy_base, yy_chk, yy_defThe transition table, "in state S, reading class c, go to state T", stored in a compressed form so it takes less memory.

Character classes, with real numbers from our lex.yy.c. A DFA table needs one column per input symbol. With 256 possible bytes that's a lot of columns, so Flex first groups bytes that behave the same everywhere. Our 256 bytes collapse into just 46 classes:

CharactersClassWhy they are grouped (or kept apart)
1 2 … 917Every rule treats them the same.
016Kept apart from 1–9, because the rules 0|[1-9]… and 0{DIGIT}+ (leading-zero error) treat 0 differently.
x z A Z _ d g j m q v y and more23Letters that appear in no keyword: for the DFA they're all just "an identifier letter".
a · e · f · i · E26 · 29 · 30 · 32 · 24Each gets its own class, because keywords (if, fn, false, …) or the exponent (e/E) need to tell them apart.
space, \t, \r2All handled by the whitespace rule. (\n is class 3: it also matters for // comments and strings.)
@ # and every non-ASCII byte1No rule except the catch-all . cares about them.

This is a real-world version of the minimization idea from Part A: merging things that behave the same makes the machine smaller.

Where does priority live? In the state "exactly if", two rules accept: the keyword and IDENT. A DFA state can only store one answer, so when building yy_accept Flex stores the rule that appears first in lexer.l. Rule priority is decided once, when the table is built, not while scanning. That's why the order of rules in our file matters.

11.4 Steps 2 and 3 · cc -c: C becomes machine code (.o files)

The C compiler translates each .c file into machine code, the instructions the processor understands. The -c flag means "compile only, don't make a program yet". The result is an object file (.o).

Each object file is incomplete on purpose, because it uses things that live in the other file. The tool nm lists the names inside an object file. This is real output, simplified:

main.olex.yy.o
Needs from elsewhere
(nm shows these as U, "undefined")		yylex, yytext, yylineno, yyin, lex_errors, plus printf, fopen, strcmp … from the C libraryonly C library functions

That's what the extern lines in main.c (§9.1) are for: they tell the compiler "yylex and friends exist somewhere else; leave a hole for them". Each "Needs" in one column is filled by a "Provides" in the other.

Why compile them separately instead of in one command? So each file can get its own flags. The generated lex.yy.c gets -Wno-sign-compare (Flex's own harmless warning, bug #1), and our main.c keeps every warning switched on.

11.5 Step 4 · linking: two halves become one program

The linker (run by the same cc command) takes both .o files and fills every hole: main.o's call to yylex is connected to the yylex in lex.yy.o. It also connects printf, fopen and the rest to the system's C library. The result, build/ankac, is a complete program you can run.

11.7 How we found a mistake in the spec this way

The generated file contains #define YY_NUM_RULES 62. Counting our rules group by group only reaches 62 with 16 keyword rules, but the spec said "15 keywords". Recounting by hand (fn, let, if, else, while, for, in, return, break, continue, print, int, float, bool, true, false) gives 16. The same check showed the spec's "10 multi-character operators" is really 13. The code was right; the numbers in the text were wrong (written by the AI). Both are now fixed and logged in docs/AI_USAGE.md, because the report must list what the AI got wrong.

14. Questions you may get in class

Why does ifx become one identifier and not IF + x?

Maximal munch. The identifier rule matches 3 characters and the keyword if only 2; the longest match wins. Priority only matters when the lengths are equal.

Why is if a keyword and not an identifier?

Both rules match 2 characters, a tie. On a tie, the rule written first wins, and we wrote the 16 keyword rules before the identifier rule.

How do you tell = from ==?

We don't write any special code. Each has its own rule, and maximal munch takes the longer match. Flex's DFA simply keeps reading as long as a longer match is possible.

What happens with an unknown character like @?

The last rule, ., matches any single character. It reports unexpected character '@' with the line number, skips that one character, and lexing continues. The lexer never stops at the first error.

Can a regular expression match nested comments?

No. Nesting needs counting, and a finite automaton has finitely many states, so it can't count without limit. We use a Flex start condition (comment mode) plus a C counter, comment_depth.

Where do the line numbers come from?

%option yylineno. Flex adds 1 to yylineno for every newline it reads, in any rule, including inside comments.

Why is 0..5 not the float 0. followed by .5?

Our float rule needs digits on both sides of the dot. 0. followed by . can never be a float, so the lexer reads INT(0), then .. (DOTDOT), then INT(5). That was a deliberate design decision.

What is lex.yy.c, and do you edit it?

It's the C file Flex generates from lexer.l: our rules as a DFA (tables) plus the yylex() function that runs it. We never edit it; we change lexer.l and let make regenerate it. It lives in build/ and isn't committed.

How does the generated code implement maximal munch?

The yylex() loop keeps following DFA transitions as long as it can, remembers the last accepting state it passed, and when stuck backs up to that position. Rule priority is decided when the table is built: if a state accepts for several rules, Flex stores the one listed first.

What does the linker do?

main.o calls yylex but doesn't contain it; lex.yy.o contains it. The linker connects the two object files (and the C library) into one runnable program, build/ankac.

How is Flex related to Part A?

Flex takes all our regexes, builds an NFA (Thompson), converts it to a DFA (subset construction), minimizes it, and writes the DFA as tables in C. It's the same pipeline we do by hand in Part A.
